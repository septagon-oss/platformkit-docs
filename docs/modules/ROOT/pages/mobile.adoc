= The native shell

{mobile-repo}[`platformkit-mobile`] is an Expo application that signs in against
`POST /api/v1/auth/login`, reads `GET /api/v1/admin/resources`, and generates a
list, a detail and a form screen for every resource the caller may reach — the
same rule the web shell follows. Custom screens are renderer packs: a plain
object mapping `module/entity` to components, passed once at the composition
root. Nothing registers itself.

== The seam

`screens.Describe` in the public repository answers with the resources the
caller may read, each with its module, entity, API path, the schema its
screens derive from, the fields a command owns, and whether this caller may
write it. An unreadable resource is not in the document at all. The golden file
{source-tree}/ui/screens/testdata/catalog.json[`ui/screens/testdata/catalog.json`]
is that document for a fixture entity; the shell carries a byte copy and its
parser test reads it, so a change to the seam the shell cannot parse fails
there. The link:{attachmentsdir}/flow-seam.html[seam flow^] draws the path
from the entity struct to both shells, and the
link:{attachmentsdir}/flow-mobile.html[native shell flow^] the session,
catalog and screen sequence.

The session is the auth module's cookie. The shell keeps the `Set-Cookie` value
it was given and sends it back as `Cookie`; the kernel's CSRF rule accepts a
caller that presents neither `Sec-Fetch-Site` nor `Origin`, because a caller
that is not a browser presents what it presents deliberately.

== The shape

[cols="1,3"]
|===
| Directory | Holds

| `src/core/`
| The catalog types and a validator that names what is wrong; `derive.ts`,
  which restates the web generator's rules — the first writable string is the
  row's name, `hide:list` hides a column, read-only fields never appear on a
  form, immutable fields are read-only on edit and absent on create, an enum is
  a picker, a bool a switch — and the value helpers an instant, a number and a
  form's own refusals go through; and a reducer for the session lifecycle. It
  imports nothing from React or React Native and is tested in plain Node.

| `src/effects/`
| Fetch with the kept cookie — login, catalog, list with sort and equality
  filters, get, create, patch, delete on the entry's own path — and the secure
  store.

| `src/ui/`
| The component library, props in and elements out, in one direction of
  imports the lint enforces: `atoms/` (a word, a button, a field, a switch, a
  choice that asks the platform's own chooser, an instant that asks its own
  date and time controls), `molecules/` (a section that is inset-grouped on
  iOS and a raised card on Android, a row, a detail row, a form field with its
  refusal), `organisms/` (the generated list, detail, form, home and sign-in
  as pure components), and `templates/` (the scroll, the large-title inset,
  the safe area, the keyboard). `theme.tsx` follows the device's appearance;
  its palette is generated from the public repository's design export, so a
  colour is written once. A gallery shows every piece in both modes.

| `src/screens/`
| Where an effect becomes a prop: one hook per generated screen owns its
  requests, a generation guard against late responses and, for the form, an
  explicit phase, so nothing saves before the row has loaded; one composition
  per screen sets the native header — large titles, Edit, Cancel and Save, the
  account menu — and renders the organism. Create and edit are a sheet.

| `src/renderers.ts`, `src/shell.tsx`, `src/route.tsx`
| The renderer-pack type, the composition root's context (the session, the
  catalog and a count of what this app wrote to each resource, so a list
  re-reads only when it is stale), and the one component every resource route
  delegates to.

| `app/`
| Expo Router files that compose and render nothing of their own.
|===

== Delivery

A native fingerprint, committed beside the source, is the hash of everything a
binary is built from; the repository's check fails when it is stale, so the
question "does this change need a new binary" is a reviewed diff. One recipe
builds the Android binary inside a pinned toolchain image, sized to fit a
small job, and a workflow builds the verification binary whenever a native
input changed. A tag builds the unsigned release outputs with their checksums;
signing happens where the key is kept, never in a workflow, and the signed
files become the release. Device journeys are Maestro flows kept in the
repository and run on a developer's emulator; the check proves they name real
elements and no more. iOS is built on a Mac by hand; there is no iOS build in
any workflow.

== Running it

[source,sh]
----
npm ci
npm run check          # typecheck, lint, format, unit tests
EXPO_PUBLIC_API_URL=http://platformkit.localhost:8080 npm start
----

== What is and is not proven

`npm run check` is green: the Node and component suites, the fingerprint and
the flow check. The verification binary was built by the recipe under the
same CPU and memory shape a small job has, installed on an Android 16
emulator, and the four flows passed against the reference application:
sign-in with the kept cookie, one task created, read, edited and deleted on
the generated screens, sign-out, and the gallery in both modes. iOS has not
run on a device; the native header, the sheet presentation and the compact
date controls there are asserted by type and test only until it does.
